# معماری فنی پیشنهادی

وضعیت: Godot + GDScript، Android، آفلاین و هستهٔ مشترک پرونده با محتوای JSON توسط کارفرما تأیید شده‌اند؛ جزئیات پیاده‌سازی پیشنهادی است. هیچ موتور یا ابزار توسعه‌ای در این مرحله نصب نشده است.

دامنه و هزینهٔ معماری در [هستهٔ پرونده و اثر بر حجم کار](08-case-engine-scope.md) مشخص شده است. داده‌محوری از نمونهٔ گام ۴ شروع و در گام ۵ تثبیت می‌شود؛ متن، جواب معما و شروط اختصاصی پرونده در کد عمومی قرار نمی‌گیرند.

## انتخاب و آماده‌سازی ابزار

مبنای پیشنهادی متن: Godot 4.x، GDScript، پرونده‌های JSON و Git. شمارهٔ دقیق موتور و export template در گام ۳ انتخاب و ثبت شود؛ در میانهٔ تولید بدون نیاز مشخص تغییر نکند.

خروجی Android به تنظیم JDK و Android SDK نیاز دارد؛ نسخه‌های دقیق با نسخهٔ انتخابی موتور تطبیق داده شوند. [راهنمای رسمی خروجی Android](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)

در صورت انتخاب iOS، مسیر رسمی خروجی به macOS و Xcode نیاز دارد؛ دسترسی به آن‌ها باید در زمان‌بندی لحاظ شود. [راهنمای رسمی خروجی iOS](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_ios.html)

## تفکیک مسئولیت‌ها

| بخش | مسئولیت | معیار مهم |
| --- | --- | --- |
| CaseLoader | خواندن و اعتبارسنجی پرونده | شناسه یا ارجاع نامعتبر پیش از بازی گزارش شود |
| CaseCatalog | فهرست محلی و پیش‌نیاز بازشدن پرونده‌ها | ورود فقط به محتوای نصب‌شده و دارای پیش‌نیاز تکمیل‌شده |
| GameState | مرجع واحد وضعیت جاری | وضعیت نمایشی با منطق پرونده ناسازگار نشود |
| ClueSystem | کشف مدرک و ارسال رویداد | کشف تکراری بدون اثر اضافه |
| DialogueSystem | نمایش متن، گزینه و شروط | امکان ادامه و خروج مشخص |
| PuzzleSystem | اجرای انواع معمای لازم | جواب و پاداش تکراری اعمال نشود |
| NotebookSystem | نمایش مدارک و هدف | با بارگذاری ذخیره بازسازی شود |
| HintSystem | راهنمای متناسب با مرحله | مدرک کشف‌شده را دوباره پیشنهاد نکند |
| ProgressSystem | ذخیره، بازیابی و اتمام | حفظ پیشرفت پس از توقف برنامه |
| InventorySystem | اشیای قابل استفاده | فقط اگر معمای انتخابی واقعاً نیاز داشته باشد |

هستهٔ پرونده مجموعه‌ای از سیستم‌های کوچک داخل بازی است؛ ساخت موتور عمومی برای هر نوع بازی هدف MVP نیست. پروندهٔ جدید برای مکانیک‌های موجود با داده و دارایی اضافه می‌شود؛ مکانیک جدید ممکن است کدنویسی بخواهد.

## ساختار پیشنهادی پروژهٔ آینده

```text
project.godot
scenes/           # منو، محیط، پنل‌ها و معماهای قابل استفادهٔ مجدد
scripts/core/     # وضعیت، بارگذاری و ذخیره
scripts/systems/  # سرنخ، گفتگو، معما و راهنما
data/cases/      # دادهٔ پرونده‌ها
assets/           # تصاویر، صداها و فونت‌ها
localization/     # متن‌های قابل ترجمه
tests/            # آزمون‌های منطق و داده
docs/             # همین مستندات
```

این درخت فقط طرح است و هنوز ایجاد نشده است.

## قرارداد داده

پروندهٔ اجرایی باید شامل `schema_version`، `case_id`، عنوان، محیط‌ها، نقاط تعامل، شخصیت‌ها، سرنخ‌ها، گفتگوها، معماها، راهنماها و شرایط پایان باشد. هر شناسه در نوع خود یکتا باشد؛ هر ارجاع به شناسهٔ موجود اشاره کند. متن‌ها UTF-8 و ترجیحاً دارای کلید ترجمه باشند.

نمونهٔ زیر صرفاً شکل دادهٔ سرنخ را توضیح می‌دهد و پروندهٔ کامل قابل اجرا نیست:

```json
{
  "schema_version": 1,
  "case_id": "bazaar_001",
  "title": "راز بازار بزرگ",
  "clues": [
    {"id": "receipt", "title": "رسید خرید", "location_id": "shop"},
    {"id": "shoe_print", "title": "رد کفش", "location_id": "shop"}
  ]
}
```

قرارداد تکمیلی در گام ۵: hotspot شامل شکل/مختصات نرمال‌شده، شرط دیده‌شدن و عمل؛ گفتگو شامل گره آغاز، گزینه، شرط و اثر؛ معما شامل نوع، ورودی، شرط حل و اثر؛ راهنما شامل مرحلهٔ مرتبط و سه سطح. شروط از عملیات محدود مانند `has_clue` و `puzzle_solved` استفاده کنند؛ متن JSON به‌صورت کد اجرا نشود.

منطق پیشنهادی تعامل: دریافت لمس ← بررسی بسته‌نبودن ورودی با پنل ← ارزیابی شرط ← تغییر وضعیت ← ذخیره ← نمایش بازخورد. برای توسعهٔ دسکتاپ ورودی ماوس هم پوشش داده شود؛ یک لمس نباید از دو مسیر دوبار پردازش شود.

## وضعیت و ذخیره‌سازی

```text
not_started -> investigating -> deduction_available -> completed
```

ورود به مرور پرونده بعد از تحقق شروط داستان مجاز است. پاسخ نادرست حالت تکمیل ایجاد نمی‌کند؛ بازیکن به مرور یا تحقیق برمی‌گردد. وضعیت صفحهٔ فعلی از وضعیت پرونده جدا باشد تا بازکردن دفتر پیشرفت را تغییر ندهد.

ذخیرهٔ پیشنهادی: JSON محلی در مسیر دادهٔ کاربر با `save_version`، `case_id`، نسخهٔ محتوا، محیط فعلی، شناسهٔ مدارک، پرچم‌های گفتگو، معماهای حل‌شده، سطح راهنما و وضعیت پایان. اشیای صحنه مستقیماً ذخیره نشوند.

تعریف ثابت پرونده با فایل پیشرفت متفاوت است. ذخیرهٔ هر پرونده جدا و فهرست پرونده‌های تمام‌شده در پیشرفت کلی ثبت شود؛ شناسهٔ مدرک در محدودهٔ `case_id` معنا دارد. پیش‌نیاز بازشدن پرونده در کاتالوگ محلی تعریف می‌شود. MVP فقط یک پروندهٔ کامل دارد؛ قابلیت بازشدن بعدی با نمونهٔ فنی کوچک آزموده می‌شود. افزودن محتوای آینده فعلاً از طریق نسخهٔ تازهٔ برنامه است و backend یا دانلود محتوا لازم ندارد.

- ذخیره پس از کشف مدرک، حل معما و تغییر مهم؛ فقط به خروج از برنامه تکیه نکند.
- نوشتن ابتدا در فایل موقت و نگهداری آخرین نسخهٔ معتبر، برای کاهش خطر قطع‌شدن هنگام نوشتن.
- فایل خراب یا نسخهٔ ناسازگار شناسایی شود؛ بازی کرش نکند و ذخیرهٔ معتبر بی‌صدا از بین نرود.
- شروع دوبارهٔ پرونده از ادامه‌دادن جدا باشد و پیش از حذف پیشرفت، تأیید درون بازی داشته باشد.
- در صورت تغییر ساختار ذخیره، راه مهاجرت یا رفتار مشخص ناسازگاری تعریف شود.

## آزمون امکان‌پذیری پیش از توسعهٔ کامل

روی گوشی واقعی: اجرای خروجی، لمس، متن فارسی، نسبت تصویر، پخش صدا، توقف/بازگشت برنامه و ذخیره/بازیابی بررسی شوند. انتخاب روش نمایش راست‌به‌چپ با قابلیت‌های موتور و آزمون فونت انجام شود. [مستندات رسمی بین‌المللی‌سازی Godot](https://docs.godotengine.org/en/stable/tutorials/i18n/internationalizing_games.html)

تاریخ مراجعه به منابع رسمی: ۲۰۲۶-۰۹-۱۷. صفحات stable ممکن است تغییر کنند؛ تنظیمات نهایی باید همراه نسخهٔ نصب‌شده ثبت شوند.
